# CardShopCoop — 1.00 Follow-ups & Limitations

Planning document for the work remaining after the 1.4.0 1.00-compatibility release.
Companion: `docs/game-1.00-breakage-report.md` (what broke and why).

## 0. Shipped in 1.4.0

Join-load scene fix, snapshot-slot fix, Ascension market, tournament sign-up gating, PvP duel
gate, and the host→client warehouse `StoredBoxRecord` channel. Wire version 104; both players
must run 1.4.0.

## 1. Workstreams

Priority: **P0** blocks/corrupts normal play · **P1** significant feature/UX gap · **P2** polish.

### F1 — Guest warehouse store/take (P0) — *designed*
The one user-visible regression from 1.4.0: guests cannot bank or take warehouse boxes.
- New channel: `WarehouseOpMessage` (client→host; `Op=Store/Take`, `RequestId`, shelf identity,
  box id/item/amount/size) + `WarehouseTakeResultMessage` (host→requester). Mirrors
  `ContainerSync`'s empty-box-storage pattern; do **not** reuse `BoxUpdate`/`ContainerOp`.
- Host store: validate lease/ownership (`HostBoxHeldByConnection`) and capacity, run vanilla
  `DispenseItem(isPlayer:false, compartment)` under a new **exact-box, non-frame-limited**
  data-only-destroy suppression (survives the lerp), then `ForgetHostBox` to emit the
  authoritative `Removed`. Never hand-add a record.
- Host take: `RestockManager.MaterializeStoredCandidate` (canonical pop+rebuild+spawn), assign a
  host id (`EnsureHostId`), send the result, force box + warehouse resync.
- Client: block local mutation, track pending by `RequestId`, auto-hold the exact authoritative
  `BoxId` when its `BoxSnapshot` arrives. Dedup per-client monotonic `RequestId`; never
  optimistically mutate record lists.
- Verified APIs exist: `TryGetHostBox`, `EnsureHostId`, `HostBoxHeldByConnection`,
  `ForgetHostBox`, `TryGetClientId`, `MaterializeStoredCandidate`, `PackageBoxCandidate`.
- **Wire:** new message DTOs → next release is a **minor** bump.
- **Acceptance:** guest store/take on multi-compartment racks; host authoritative; no
  duplication/loss; double-click and racing take safe; 0.70.3-styled builds stay inert.

### F2 — Live-test + native-save verification (P0)
- Two-client end-to-end on real 1.00: join/load, warehouse store/take on a 4-compartment rack,
  Ascension prices, tournament sign-up, TCG gate, day-end, save transfer, mid-session rejoin.
- **Native/Game Pass save backend is a P0 operational risk:** 1.00 uses
  `PlatformManager.UseNativeSaves()` and `SaveNative("GameData_<slot>", …)` instead of slot JSON
  files. The mod's in-memory serialization path is conceptually sound, but must be tested on
  native-save hardware: async `SaveNative` vs the sampled save counter, `m_SavedGame` staleness,
  the guest's container overwriting the injected world before `PropagateLoadData`, and native
  slot-6 handling not touching the UI list. A failure here means "guest loads its own world".
- Deliverable: a findings list; only then new code.

### F3 — Playable TCG (P1) — *scoped*
The duel is fully local: `PlayTableGame`/`PlayCardSet` hold the match in memory with no
serialization, and `PlayTableSaveData` saves only table/shop state. **No seeded RNG** — all
match randomness is global `UnityEngine.Random` — so seed-only lockstep is not viable.
- **(A) Host-only + UX** (0.5–2 days): clearer "the host starts duels" message; stop a guest
  reserving the second seat; document it. *Recommended.*
- **(B) Guest spectator** (~3–6 weeks): host snapshot+event stream, rebuild visuals, reconnect.
- **(C) Full two-player netcode** (~8–16+ weeks): action requests, host validation, hidden
  info, RNG ownership, reconnect.
If B is ever pursued, start with a **read-only host duel snapshot probe**, not full sync.

### F4 — Cheats (P1 if reachable, else P2) — *audited*
`CheatManager`/`CheatCanvasController` can add coins/XP and alter grades, prices, game speed,
customers, instant grading/checkout (`CheatManager.cs:68-80`, `CheatCanvasController.cs:498-560`).
Entry points F1/controller sequences exist. The mod references none of it. `CheatManager` calls
`Destroy` in `Start` (`:113-116`) so it may be debug-only — reachability needs confirming.
- Recommended: **block/neutralize on clients** (host owns economy) rather than sync.
- Severity: P1 if reachable, P2 if confirmed debug-only.

### F5 — Graded-card opening reveal for guests (P2) — *audited*
The guest blocks `InteractablePackagingBox_Card.OnPressOpenBox`, so it misses the new
`GradedCardOpeningSequence`. Cards are still granted via `ClientCollect`. Vanilla `OpenScreen`
**grants cards again** (`GradedCardOpeningSequence.cs:95-108`), so it must not be called
directly. A safe fix is a **presentation-only** reveal path: snapshot the local card data, wait
for the host grant/ack, animate without calling `CPlayerData.AddCard`. Naïve reuse risks
duplicate cards (P1).

### F6 — Save/state completeness (P1 for tournaments/TCG, else P2) — *audited*
- `PlayTableSaveData.isPlayerSeat` (`:23-29`) is not in `PlayTableSync.SeatState` — player-seat
  ownership can be lost on reconstruction (P1 for TCG, P2 otherwise).
- New `CGameData` fields (`m_PlayerTournamentData`, `m_IsPlayerRegisteredForTournament`,
  Ascension lists, `m_EntitlementsBonus`) ride the serialized join transfer, but are **not
  live-synced** afterwards; tournament state can go stale/overwritten (P1).
- `CEventPlayer_GrantEntitlementsBonus` is unhandled; deluxe/preorder unlock state can diverge
  (P2, P1 if it gates content).

### F7 — New-content coverage (P2) — *audited*
New `EObjectType` pre-order/deluxe objects and +55 `EDecoObject` are covered by the **generic**
enum/placed-object/deco sync — no per-member code needed. Only risk is platform-exclusive
prefabs resolving to null on the other platform. **FoodieGO is a stub** in 1.00 (enum/pack
entries only, no card data or market table) — no market sync work justified; keep the existing
`default: return false`.

### F8 — Local-only (no work) — *audited*
Screenshots (already excluded from sidecar), skins/customization, `GameTransitionManager`,
`VertexLightProbe(s)`, `DevMultiItemScreenshot`. No shared state.

### F9 — Robustness/observability (P2)
- Event-driven warehouse resend (force on record change) instead of the current 1.5 s poll.
- Verify warehouse racks are `PlacedObjectIdentity`-bound on clients (the `ShelfId` fast path).
- Update `docs/game-1.00-breakage-report.md` with implemented status.
- (Optional) Unity 6 `FindObjectOfType`/`enableWordWrapping` deprecation cleanup.

## 3. Limitations / deliberate non-goals

- **Exact version handshake is intentional.** Cross-version joins stay unsupported; every wire
  change means both players update.
- **One-sided modded content** cannot be represented on the peer; unmappable stored boxes are
  omitted rather than shown as blanks.
- **TCG match state** may remain out of scope (F3 decision); the current gate prevents desync.
- **Full two-player TCG netcode** is not a normal state-replication task (local ownership,
  global RNG, hidden information, async effect UI) — only pursue with an explicit budget.
- **Cheats** may be treated as out of scope if confirmed unreachable.
- **Native-save platforms** are only supported to the extent the in-memory path is verified.

### B4 detail (confirmed from logs)

`CardShopCoop_*.log` shows, 19×:
```
[Warning:CardShopCoop] NPC dressing 'Male17': Index was out of range. Must be non-negative and less than the size of the collection.
```
`CC.CharacterCustomization.Initialize()` → `LoadFromJSON()` → `ApplyCharacterVars()` iterates the
*preset's* `ApparelNames`/`HairNames` and indexes the clone's `ApparelTables[slot]`/`HairTables[slot]`

customer (no clone/preset mismatch), so it dresses correctly.

- Likely correct fix: mirror the host customer's `CC_CharacterData` (or model index + gender) and apply

## 7. Cross-version warehouse backends (game 1.00 vs game 1.0)

The warehouse module now has **two backends** and picks one at startup; the single DLL runs on
either game build.

| | backend | owner of warehouse rack contents |
|---|---|---|
| game 1.00 | `StoredBoxRecord` list on each `ShelfCompartment` (all reflection) | WarehouseBoxSync (records) |
| game 1.0 | live `InteractablePackagingBox_Item` objects held by the compartment | the normal box channel |

Selection: `_records` = the whole 1.00 record API resolved; `_liveUsable` = the live model resolved
**and** `StoredBoxRecord` absent. `Available()` is `_records || _liveUsable`. If `StoredBoxRecord`
exists but part of its API did not resolve, the module stays **inert and logs an error** rather than
driving the live recipe against record storage.

**One owner per backend.** That is why `ItemBoxFamily.ApplyStored` branches on `HasRecordStorage`
(record storage model present) and *not* on `Available()`: on a live build `Available()` is true too,
but a stored box there is a real object the box channel already owns. Keying the park/hide branch off
`Available()` hid rack boxes the channel still owned (guest's racks rendered empty) and could not be
repaired.

Store/take are **forwarded on both backends**, so rack membership has one owner (the host). The
prefixes are installed everywhere and only no-op when this machine is the host or a state is being
applied. Letting a live guest take vanilla-locally was a bug: the host applied the Held claim without
un-hooking its own racked copy, so its snapshot read `Held+Stored` and the client's stored-while-held
rule then undid the take.

`WarehouseState` carries the normalised ordered `(itemType, amount, big)` list per compartment plus
`HostLiveBoxes`, so a live host and a record host emit the same message and each side realises the
state in its own model.

### Support matrix

| session | warehouse |
|---|---|
| 1.00 host + 1.00 guest | full (record backend) |
| 1.0 host + 1.0 guest | full via the box channel + forwarded ops |
| 1.0 host + 1.00 guest | full **only with `AllowCrossBuildJoin` set on the host (default off)**. The host serves the normalised state and answers ops; the guest rebuilds **records**. A forwarded store drops the guest's possession lease on the host (`BoxEngine.ReleaseLease`) so the snapshot becomes `Free+Stored`, and the guest yields a held box the authority says is stored (`storedWhileHeld` in the box apply) - without both, the guest stayed holding an invisible box. |
| 1.00 host + 1.0 guest | full **only with `AllowCrossBuildJoin` set on the host (default off)**. The host advertises `HostLiveBoxes=false`; the live guest **forwards** store/take to the host (like every client) and **materialises** the entries as real stored boxes (`SpawnPackageBoxItem` + `DispenseItem`), tearing the replaced ones down through the game's own `OnDestroyed`. |

`WarehouseStateMessage.HostLiveBoxes` (appended last) is what tells a live guest whether to
materialise (record host) or leave the racks to the box channel (live host). Both are one owner.

### Wire / version

The added field changes the message layout, which `AGENTS.md` normally makes a **minor** bump. It
deliberately stays on **1.4.0 / wire 104** because 1.4.0 is unreleased and both machines update
together. Consequence: `PluginHash` is `guid=version`, so a stale 1.4.0 build still passes the
handshake. The wire is JSON with `MissingMemberHandling.Error`, so the mismatch does **not**
mis-parse - the stale peer **drops every `WarehouseState` frame** (rate-limited warning), and now
that the periodic heal is gone its warehouse channel stays dead until it updates.
**Both players must run the same build.**

### Heal

The old 1.5 s poll and 12 s heal were replaced by change events plus a bounded local retry. A
warehouse state that arrives before the guest's racks exist is re-applied locally from
`OnClientTick` until every compartment resolves (`_pendingApply` / `_pendingApplied`, plus
`_refusedCompartments` so a rack that genuinely refuses its entries is torn down once), capped at
`PendingApplyAttemptCap` (600 passes).

Eventual correctness comes from a **gradual sweep**, not a periodic full resend: the host's
`PeriodicUpdate` emits ONE compartment every `SweepSliceSeconds` (5 s), round-robin, so the whole
warehouse re-asserts over time and a dropped frame heals without a burst. The complete state is only
sent per-connection, from `FullUpdate(connId)` (the join catch-up path). `ForceResend()` stays the
event-driven heal. See AGENTS.md, "Sync scheduling: no periodic full resends".

### Known gaps (verify before enabling mixed sessions by default)

- `ShelfCompartment.ArrangeBoxItemBasedOnItemCount` re-orders records with no hook (unreachable in
  1.00 as shipped), so record *order* can drift until the next membership change. Cosmetic.
- Mixed game-version sessions are **rejected by default**: the Hello handler compares the game-build
  fingerprint (`Application.version` / `unityVersion`) and refuses a mismatch unless the HOST sets
  `AllowCrossBuildJoin = true` (default false). The mod's own warning applies - two different game
  builds can corrupt each other's saves, so back up before playing. Mod-version and enum/registry
  parity still apply on top of that opt-in.
- The live-guest materialisation path (1.00 host + 1.0 guest) cannot be exercised on a machine
  without the legacy build; it is code- and decompilation-verified only.
